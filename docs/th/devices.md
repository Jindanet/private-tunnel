# PrivateTunnel Device

[ภาพรวม](../../README.th.md) · [เอกสารภาษาอังกฤษ](../en/devices.md)

ผมแยกไคลเอนต์สำหรับบอร์ด เพราะ Node.js หน้าต่างรับข้อมูลขนาดใหญ่ และการส่งต่อ socket แบบทั่วไปไม่เหมาะกับข้อจำกัดของ ESP8266 ไลบรารีนี้จึงทำงานเล็กลง: เชื่อม TLS ออกไป ตรวจใบรับรอง รับ HTTP ครั้งละหนึ่งคำขอ แล้วเรียกฟังก์ชัน C++ เพื่ออ่านเซนเซอร์หรือสร้างคำตอบ

ส่วนอุปกรณ์ยังเป็น **รุ่นทดลอง** ไลบรารี **0.1.1** และโปรโตคอล **`ptunnel.device.v1`** มีการทดสอบกับเซิร์ฟเวอร์จริงและคอมไพล์ BasicHttp, ProvisionedHttp และ WakeOnLan บน CI ด้วย core ESP32 **3.3.12** กับ ESP8266 **3.1.2** ผลเหล่านี้ยังไม่ใช่การทดสอบบอร์ดจริงหรือผลวัด RAM สูงสุด

## เลือกบอร์ด

| อุปกรณ์ | แนวทางตอนนี้ |
| --- | --- |
| ESP32 ที่ใช้ Arduino core | ใช้ไลบรารีโดยตรง เริ่มจากบอร์ดพัฒนาที่มี USB จะสะดวก |
| ESP8266 รวมถึง NodeMCU | ใช้ HTTP แบบจำกัดขนาดเดียวกัน ต้องตรวจ RAM ที่เหลือ |
| บอร์ดชื่อ Arduino ที่ใช้ชิป ESP32 | ใช้แพ็กเกจและการตั้งค่าขาของบอร์ดนั้น |
| Uno R3 หรือ AVR รุ่นดั้งเดิม | ใช้ตัวกลาง SRAM 2 KiB ไม่เหมาะกับ TLS client ชุดนี้ |
| ชิปอื่น หรือ ESP-IDF ที่ไม่ใช้ Arduino | ยังไม่รองรับ |

รุ่นนี้ใช้ API และข้อจำกัดเหมือนกันทั้งสองชิป ESP32 ยังไม่มีโหมดสองงานพร้อมกันหรือ TCP ที่เคยเสนอไว้

## ติดตั้งผ่าน Arduino IDE

1. อัปเดตเซิร์ฟเวอร์เป็น **1.4.0 ขึ้นไป** คง `REQUIRE_DATA_TRANSPORT_V4=true` ได้ ไม่ต้องลดข้อกำหนดของเดสก์ท็อป
2. เปิดหน้าตั้งค่าของแอดมิน ส่วนรหัสเชื่อมต่อ เลือก **อุปกรณ์ ESP32 / ESP8266** แล้วสร้างรายการ เก็บ **รหัสเชื่อมต่อ** และ **รหัสผ่านเข้าชมเว็บ** ทันที หลังจากนี้เซิร์ฟเวอร์เก็บเฉพาะแฮช
3. ดาวน์โหลด `PrivateTunnelDevice-v1.4.1-arduino.zip` จาก[หน้าดาวน์โหลด](https://github.com/Jindanet/private-tunnel/releases) แล้วใช้ **Sketch → Include Library → Add .ZIP Library** หรือคัดลอก [`device/PrivateTunnelDevice`](../../device/PrivateTunnelDevice) ทั้งโฟลเดอร์ไปไว้ใน `libraries` ของสมุดสเก็ตช์ ภายในมี `library.properties` กับ `src` โดยตรง หากไม่เห็นให้เปิด IDE ใหม่ ไม่ต้องติดตั้ง WebSocket เพิ่ม
4. เพิ่มที่อยู่รายการบอร์ดให้ตรงชิปในหน้าตั้งค่า IDE:

   ESP32: `https://espressif.github.io/arduino-esp32/package_esp32_index.json`

   ESP8266: `https://arduino.esp8266.com/stable/package_esp8266com_index.json`

5. ติดตั้ง core เลือกบอร์ดจริงกับพอร์ต USB เปิด **File → Examples → PrivateTunnelDevice → ProvisionedHttp** แล้วอัปโหลด
6. เปิด Serial Monitor ที่ **115200**

เป้าหมายที่คอมไพล์บน CI คือ `esp32:esp32:esp32` กับ `esp8266:esp8266:nodemcuv2` บอร์ดอื่นอาจต้องเปลี่ยนไดรเวอร์ USB ขนาด flash พาร์ทิชัน หรือขาปุ่มตั้งค่า ตัวอย่างใช้ **GPIO 0** อย่ากดค้างขณะรีเซ็ต เพราะอาจเข้าโหมดอัปโหลดของชิปแทนการรันโปรแกรม

## บันทึกค่าครั้งเดียว

บอร์ดที่ยังไม่มีค่าจะเปิด Wi-Fi ชั่วคราวชื่อ **`PrivateTunnel-Setup`** ใช้รหัส WPA2 แบบสุ่มที่แสดงใน Serial Monitor เชื่อมต่อแล้วเปิด **`http://192.168.4.1/`** หน้าตั้งค่าปิดหลังห้านาทีหากยังไม่บันทึก หน้านี้อยู่ในเครือข่ายตั้งค่า ไม่ใช่เว็บสาธารณะของ tunnel

| ช่อง | กรอกอะไร |
| --- | --- |
| ชื่อและรหัส Wi-Fi | เครือข่ายที่จะให้บอร์ดเชื่อมต่อประจำ |
| ชื่อเซิร์ฟเวอร์ | เช่น `admin.example.com` ไม่ใส่ scheme หรือ path |
| path ของ WebSocket | คัดลอกแบบเต็มจากแอดมิน ปกติ `/_private-tunnel/ws` |
| กุญแจอุปกรณ์ | รหัส `ptk_...` ที่สร้างเป็นประเภทอุปกรณ์ |
| โดเมนเผยแพร่ | เช่น `apps.example.com` เว้นว่างเพื่อใช้โดเมนแรกที่อนุญาต |
| ชื่อย่อย | เช่น `sensor-one` เว้นว่างเพื่อรับชื่อที่ระบบเลือก |
| ใบรับรองราก | PEM ของรากที่ตรวจสอบชุดใบรับรองเซิร์ฟเวอร์ได้ ตัวอย่างนี้รับไม่เกิน 2047 ตัวอักษร |

กดบันทึกแล้วเชื่อมโทรศัพท์หรือคอมกลับ Wi-Fi ปกติ บอร์ดรีสตาร์ต ต่อ Wi-Fi รับเวลาผ่าน SNTP ตรวจใบรับรองกับชื่อเซิร์ฟเวอร์ แล้วเปิด tunnel ดูที่อยู่ที่พิมพ์ใน Serial Monitor และเติม **`/status`**

หากต้องเปลี่ยนค่า ให้รีเซ็ตตามปกติ แล้ว **กด BOOT/FLASH ภายในสามวินาทีแรกหลังเริ่มโปรแกรม** ปล่อยปุ่มในจังหวะรีเซ็ต หากรหัสถูกปฏิเสธ โปรแกรมหยุดลองซ้ำจนกว่าจะตั้งค่าหรือเริ่มใหม่

ตัวอย่างนี้ใช้ **พื้นที่จำลอง EEPROM** โดยเฉพาะ อย่านำไปรวมกับโปรแกรมที่ใช้ EEPROM เดียวกันโดยไม่แก้การจัดเก็บ รหัส Wi-Fi กุญแจ และ CA ถูกเก็บ **โดยไม่เข้ารหัส** ผู้ที่อ่าน flash ได้อาจนำรหัสออกมาได้ เขียน flash เฉพาะตอนกดบันทึก ส่วนตัวอย่าง `BasicHttp` กำหนดค่าในสเก็ตช์และไม่มีหน้าตั้งค่า

## TLS และใบรับรอง

ไคลเอนต์นี้ใช้ TLS เสมอ ไม่มีตัวเลือกข้ามการตรวจใบรับรองหรือถอยกลับไปเชื่อมแบบไม่เข้ารหัส ขอใบรับรองรากจากผู้ออกใบรับรองหรือผู้ดูแลผ่านช่องทางที่เชื่อถือได้ ไม่ควรใช้ใบรับรองปลายทางแทนรากระยะยาว เซิร์ฟเวอร์ต้องส่งใบรับรองตัวกลางครบ และต้องเปลี่ยน CA ที่บันทึกไว้ก่อนเปลี่ยนรากความเชื่อถือ

CA ใน `BasicHttp` เป็นข้อความตัวอย่างที่ต้องแทนด้วย PEM จริงก่อนเชื่อมต่อ หน้าตั้งค่าก็ต้องใช้รากจริงเช่นกัน ต้องมีเวลาที่ถูกต้องเพื่อตรวจช่วงอายุใบรับรอง ให้เข้าถึง SNTP ได้หรือเตรียมนาฬิกาที่เชื่อถือได้ในเฟิร์มแวร์ของคุณ แก้สาเหตุเมื่อชื่อโฮสต์ DNS เวลา หรือชุดใบรับรองผิด

ยังใช้ buffer ของ TLS ตามปกติใน core **frame ของ tunnel ขนาด 512 ไบต์ไม่ได้ทำให้ buffer TLS เหลือ 512 ไบต์** รุ่นแรกยังไม่เจรจา TLS record ขนาดเล็ก ไม่ได้เพิ่ม session resumption เอง และยังรับประกันไม่ได้ว่าการ handshake จะไม่บล็อก

## เข้าใช้งานเว็บของบอร์ด

เปิด `https://sensor-one.apps.example.com/status` ใช้ชื่อผู้ใช้ **`device`** และ **รหัสผ่านเข้าชมเว็บ** หากเรียกจากสคริปต์:

```bash
curl -H "Authorization: Bearer $DEVICE_VISITOR_TOKEN" https://sensor-one.apps.example.com/status
```

ค่าเริ่มต้นให้เซิร์ฟเวอร์ตรวจก่อนส่งคำขอไปที่บอร์ด กุญแจเชื่อมต่อใช้แทนรหัสเข้าชมไม่ได้ กุญแจเดสก์ท็อปเชื่อมเป็นอุปกรณ์ไม่ได้ และกุญแจอุปกรณ์เข้าโปรโตคอลเดสก์ท็อปไม่ได้

การเปลี่ยนกุญแจจะเปลี่ยน **ทั้งสองรหัส** และตัดการเชื่อมต่อเดิม ต้องอัปเดตกุญแจในบอร์ดกับรหัสผ่านของผู้ชม ชื่อที่จองยังคงอยู่เมื่อใช้ ID กุญแจและตัวตนบอร์ดเดิม การเพิกถอนยกเลิกไม่ได้ อย่าใส่รหัสทั้งสองใน query ของ URL

### ใช้หน้าเข้าสู่ระบบของบอร์ดเอง

เซิร์ฟเวอร์ **1.4.1 ขึ้นไป** ให้แอดมินปิด **ให้ผู้ชมกรอกรหัสผ่านก่อนเข้าเว็บ** ในรายการกุญแจอุปกรณ์เดิมได้ คำขอถัดไปจะเปิดตรงไปที่หน้าเว็บของเฟิร์มแวร์ ไม่มีหน้าต่างล็อกอินของเบราว์เซอร์ซ้อน การเปลี่ยนมีผลทันที ไม่เปลี่ยนกุญแจ ไม่ตัดบอร์ด และไม่ต้องแฟลชใหม่ กุญแจใหม่ยังเปิดการยืนยันผู้ชมเป็นค่าเริ่มต้น แต่เลือกปิดตอนสร้างได้

เมื่อปิด เฟิร์มแวร์ต้องตรวจสิทธิ์ทุกคำสั่งที่ต้องป้องกันเอง บอร์ดยังต้องใช้กุญแจเชื่อมต่อเสมอ เปิดการยืนยันผู้ชมกลับได้ และรหัสผ่านปัจจุบันยังใช้ได้ ค่านี้เก็บแยกตามกุญแจอุปกรณ์ มีผลกับทุกบอร์ดที่ใช้กุญแจนั้น

เซิร์ฟเวอร์ **1.4.1 ขึ้นไป** ส่ง content type กับ body ดิบตามจริง รองรับ `text/plain` ข้อมูลฟอร์ม ไบนารี และ JSON ภายใต้ขนาดเดิม หากเบราว์เซอร์ส่ง `Origin` มา ต้องตรงกับชื่อ HTTPS ของเว็บนั้น ให้ GET/HEAD ใช้อ่านข้อมูล ฟังก์ชันต้องตรวจ method รูปแบบข้อมูล ค่า และสิทธิ์คำสั่งเอง ไลบรารีไม่ได้แปลรหัสหรือ JSON ให้ `DeviceRequest::contentType` เป็นอาร์เรย์ตัวอักษร ไม่ใช่ pointer ที่เป็น null ได้

### ตัวอย่างสั่งเปิดคอมผ่านเครือข่าย

เปิด **File → Examples → PrivateTunnelDevice → WakeOnLan** ตั้ง Wi-Fi ชื่อ/path เซิร์ฟเวอร์ กุญแจอุปกรณ์ CA จริง โดเมน MAC เป้าหมาย ที่อยู่ broadcast และ `WEB_PASSWORD` ที่รัดกุม ค่าที่ให้มาเป็นตัวอย่าง ปิด **ให้ผู้ชมกรอกรหัสผ่านก่อนเข้าเว็บ** ของกุญแจนั้นหากต้องการให้มีหน้าเข้าสู่ระบบของตัวอย่างเพียงชั้นเดียว

หน้าเว็บส่ง `text/plain` เป็นชื่อผู้ใช้ ขึ้นบรรทัดใหม่ แล้วรหัสผ่าน บอร์ดตรวจทั้ง `/login` กับ `/wake` เบราว์เซอร์เก็บรหัสในหน่วยความจำจนออกจากระบบหรือปิดหน้า ไม่มีเซสชันฝั่งเซิร์ฟเวอร์ ลองผิดห้าครั้งล็อกหกสิบวินาที และเว้นคำสั่งเปิดคอมสิบวินาที คำตอบสำเร็จหมายถึงส่ง magic packet แล้ว ไม่ใช่ยืนยันว่าคอมบูตสำเร็จ

ESP กับคอมต้องอยู่ใน LAN ที่ส่ง broadcast ตามค่าที่ตั้งได้ เปิด Wake-on-LAN ในเฟิร์มแวร์/การ์ดเครือข่ายของคอม และให้มีไฟเลี้ยงกับเครือข่ายระหว่างพัก UDP ส่งภายในจากบอร์ด ไม่ได้เพิ่ม UDP tunnel ให้ PrivateTunnel ต้องแก้เวลาและใบรับรองให้เชื่อมต่อผ่านก่อน [ซอร์สตัวอย่าง](../../device/PrivateTunnelDevice/examples/WakeOnLan/WakeOnLan.ino)

## เขียนฟังก์ชัน

ดูตัวอย่างสมบูรณ์ที่ `BasicHttp.ino` เตรียม Wi-Fi เวลา และข้อความการตั้งค่าที่มีอายุการใช้งานยาวพอก่อนเรียก `begin`

```cpp
#include <PrivateTunnelDevice.h>
PrivateTunnelDevice tunnel;

void registerRoutes() {
  tunnel.onHttp("/status", [](const DeviceRequest& req, DeviceResponse& res) {
    if (strcmp(req.method, "GET") != 0) {
      res.json(405, "{\"error\":\"GET required\"}");
      return;
    }
    res.json(200, "{\"online\":true}");
  });
}

void loop() {
  tunnel.poll();
  // งานอื่นที่ใช้เวลาสั้น
}
```

| API | ข้อตกลง |
| --- | --- |
| `onHttp(path, handler)` | สูงสุดแปดเส้นทาง เทียบ path แบบตรงตัวรวม query ต้องเก็บข้อความ path ไว้ตลอดการใช้งาน |
| `begin(config)` | ตรวจค่าและเตรียม TLS จากนั้น `poll()` ดูแลการเชื่อมต่อ |
| `poll()` | เรียกบ่อย ประมวลผล WebSocket ขาเข้าสูงสุดสอง frame และส่งคำตอบหนึ่งชิ้นต่อครั้ง |
| `online()`, `publicUrl()`, `lastError()` | สถานะ ที่อยู่ และเหตุขัดข้องล่าสุด ไม่พิมพ์กุญแจ |
| `stop()` | ตัดการเชื่อมต่อและหยุดลองใหม่ เรียก `begin()` เพื่อเริ่มด้วยค่าใหม่ |
| `DeviceRequest` | method, path/query, content type และเนื้อหาดิบสูงสุด 1024 ไบต์ ใช้ `bodyLength` เป็นความยาวจริง |
| `response.json(...)` / `text(...)` | คัดลอกเนื้อหาสูงสุด 512 ไบต์ คืน false หากค่าผิดหรือยาวเกิน |
| `response.send_P(...)` | ส่งจาก PROGMEM เป็นชิ้น pointer ต้องยังใช้ได้จนส่งเสร็จ |

`DeviceConfig` มี `host`, `port` เริ่มต้น 443, `path`, `key`, `caCertificate`, `clientId`, `domain`, `subdomain` ข้อความเป็นการอ้างอิง ไม่ได้คัดลอก จึงต้องเก็บไว้ตลอดที่เชื่อมต่อ `clientId` เป็นชื่อระบุรายการที่คงเดิม ไม่ใช่กุญแจยืนยันตัวตน ตัวอย่างตั้งค่าใช้ MAC ของบอร์ดเป็นฐาน

เรียกฟังก์ชันหลังรับเนื้อหาคำขอครบ ให้คืนการทำงานเร็วเพื่อให้เครือข่ายกับ watchdog ทำงานต่อได้ ถ้าไม่เตรียมคำตอบ ระบบตอบ 404 ห้ามเก็บออบเจ็กต์ response ไว้ตอบทีหลัง เลือกส่งจาก flash สำหรับข้อมูลคงที่ขนาดใหญ่ รุ่นนี้ยังไม่มีการจับเส้นทางแบบยืดหยุ่น API สำหรับ header ตามใจ ตัวสร้าง SSE หรือการส่งต่อเว็บเซิร์ฟเวอร์ที่มีอยู่แล้ว

## ขนาดและหน่วยความจำ

| รายการ | ทั้งสองชิป |
| --- | --- |
| tunnel / คำขอที่กำลังทำ | หนึ่งต่อการเชื่อมต่อ / หนึ่ง |
| payload / ส่วนหัวโปรโตคอล | 512 / 8 ไบต์ |
| สิทธิ์ส่งเริ่มต้น | 512 ไบต์ต่อทิศทางต่อคำขอ |
| เนื้อหาคำขอทั้งหมด | 1024 ไบต์ รวมคำขอแบบ chunked |
| path รวม query | 192 ไบต์ |
| content type | 64 ไบต์ |
| คำตอบที่คัดลอกเข้าหน่วยความจำ | 512 ไบต์ |
| เส้นทาง | แปด |
| ID บอร์ด / โดเมน / ชื่อย่อย | 48 / 253 / 63 ไบต์ |

buffer ของโปรโตคอลและคำขออยู่ในออบเจ็กต์ C++ ขนาดคงที่ ส่วน Wi-Fi, TLS, การอ่านใบรับรอง, core และเว็บตั้งค่าชั่วคราวจองหน่วยความจำเพิ่ม ตัวอย่างตั้งค่ายังเก็บโครงสร้างค่าของตัวเองและพิมพ์ `sizeof(tunnel)`, `sizeof(settings)` กับ heap ที่เหลือให้ดู รายงาน RAM ตอนคอมไพล์ไม่ใช่ผลวัด heap สูงสุดตอน TLS

เอกสาร BearSSL ของ ESP8266 อธิบาย stack ประมาณ **6 KiB และ buffer ต่อการเชื่อมต่อประมาณ 22 KiB** ก่อนรวมงานส่วนอื่น จึงไม่ควรบอกว่าไคลเอนต์ทั้งหมดใช้เพียง 4–6 KiB หลีกเลี่ยง TLS อีกเส้นทาง JSON ขนาดใหญ่ หรือเว็บเซิร์ฟเวอร์อีกตัวจนกว่าจะวัดแล้วว่าพอ [เอกสาร BearSSL ของ ESP8266](https://arduino-esp8266.readthedocs.io/en/3.1.2/esp8266wifi/bearssl-client-secure-class.html)

เซิร์ฟเวอร์ตอบ **503** เมื่อมีงานอยู่ **413** เมื่อ body เกิน และ **431** เมื่อข้อมูลเส้นทางยาวเกิน ไม่บังคับให้ body เป็น JSON ฟังก์ชันบนบอร์ดยังปฏิเสธรูปแบบที่ไม่รองรับเองได้ ไม่สะสมคิวบนบอร์ด เมื่อผู้ชมตัดการเชื่อมต่อจะยกเลิกงาน คืนสิทธิ์ส่งคำตอบหลังปลายทาง HTTP รับข้อมูลไปแล้ว

## โปรโตคอล

ใช้ WSS subprotocol `ptunnel.device.v1` บนที่อยู่เชื่อมต่อเดิม แต่ละข้อความ WebSocket แบบ binary ที่ไม่แบ่ง fragment มีหัวแปดไบต์แบบ big-endian: type, flags ศูนย์, stream ID 16 บิต, ความยาว payload 16 บิต และ reserved ศูนย์ 16 บิต stream ศูนย์ใช้กับทั้งการเชื่อมต่อ ไม่ใช้ Base64 หรือ compression

| ข้อความ | เนื้อหา |
| --- | --- |
| HELLO (1) | รุ่น 8 บิต ขนาด frame 16 บิต จำนวนงาน 8 บิต หน้าต่างรับ 16 บิต ความยาวข้อความสี่ค่าอย่างละ 8 บิต แล้วตามด้วย ID/โดเมน/ชื่อย่อย/รุ่นบอร์ดแบบ ASCII |
| READY (2) | ขนาด frame 16 บิต จำนวนงาน 8 บิต หน้าต่าง 16 บิต ขนาด body 16 บิต ความยาว URL 16 บิต แล้ว URL |
| OPEN (3) | ความยาว method 8 บิต path 16 บิต content type 8 บิต แล้วข้อความเหล่านั้น |
| DATA (4) | ข้อมูลดิบที่ไม่ว่างและไม่เกินสิทธิ์ส่งคงเหลือ |
| END (5) | ไม่มีเนื้อหา จบทิศทางหลัง DATA |
| CREDIT (6) | จำนวนไบต์ที่ใช้แล้ว 16 บิต ต้องเป็นบวกและไม่เกินหน้าต่าง |
| CANCEL (7) | ยกเลิกงาน ไม่มีเนื้อหา |
| ERROR (8) | เหตุขัดข้องระดับการเชื่อมต่อ เฟิร์มแวร์หยุดโดยไม่เผยรหัส |
| PING/PONG (9/10) | ตรวจการเชื่อมต่อ ไม่มีเนื้อหา |
| RESPONSE (11) | สถานะ 16 บิต 200–599 ความยาว content type 8 บิต แล้วข้อความ |

รุ่นแรกตกลงค่าตายตัวหนึ่งงาน frame และหน้าต่าง 512 ไบต์ ไม่ใช้ stream ID ซ้ำในการเชื่อมต่อเดียว ตัวแปลงฝั่งเซิร์ฟเวอร์ส่งต่อเข้ารูปแบบภายในของ manager ส่วนไคลเอนต์เดสก์ท็อปยังต้องใช้ v4 บนสาย ไม่ได้เปิดโหมดเดสก์ท็อปรุ่นเก่า

เชื่อมใหม่โดยเพิ่มช่วงรอจากหนึ่งถึงหกสิบวินาทีพร้อมสุ่มเพิ่ม งานที่ขาดไม่ทำต่อจากจุดเดิม heartbeat ของเซิร์ฟเวอร์และตัวจับเวลา 90 วินาทีของเฟิร์มแวร์ตรวจการเชื่อมต่อค้าง TLS handshake อาจใช้เวลาหลายวินาที จึงต้องแยกงานควบคุมที่มีเส้นตายแน่นอนออกจากงาน tunnel

## ทดสอบบนบอร์ดจริงก่อนใช้งานต่อเนื่อง

วัด heap ต่ำสุด ก้อนว่างใหญ่สุด และช่วง handshake สูงสุดด้วยชุด CA กับสเก็ตช์จริง ทดลอง Wi-Fi หลุดซ้ำ DNS/SNTP ใช้ไม่ได้ ใบรับรองผิด เปลี่ยนกุญแจ ผู้ชมยกเลิกกลางทาง อัปโหลด 1024 ไบต์ ปฏิเสธข้อมูลเกิน ส่งไฟล์ flash ยาว และเปิดต่อเนื่อง ตรวจ watchdog กับเวลาของงานเซนเซอร์ด้วย การคอมไพล์และไคลเอนต์จำลองใน CI ยังแทนการวัดเหล่านี้ไม่ได้

หาก RAM ไม่พอ ใช้ตัวกลางกับเว็บบนบอร์ดได้ทันที:

```bash
node ptunnel.js http 192.168.1.50:80
```

ตัวกลางต้องเข้าถึงเว็บของบอร์ดได้และเปิดค้างไว้ วิธีนี้เป็น HTTP ผ่าน CLI ปกติ ต้องมีการยืนยันผู้ชมจากแอปหรือระบบหน้าบ้านเอง ไม่ได้รับกติกา visitor token ของโหมดอุปกรณ์โดยอัตโนมัติ
