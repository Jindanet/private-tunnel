# PrivateTunnel 1.1.0 — release candidate notes

Prepared on 15 October 2026. This checkout contains versioned source, migration notes, tests and an artifact workflow. It does not by itself create a remote tag or publish a GitHub Release.

The release focuses on a simpler Thai/English desktop workflow, safer control-plane defaults and repeatable verification. It remains intended for personal use or a small trusted team. Public multi-user isolation is not implemented.

## Before upgrading

Read the [upgrade guide](../README.md#upgrade-from-10-to-11). Back up databases, `.env`, private state and client profiles. Existing MySQL installations must explicitly keep `DB_PROVIDER=mysql` if they relied on the previous default. The new default is SQLite, internal listeners use loopback, mirrors/bootstrap copying are off by default, and old query-token clients require temporary compatibility opt-in.

Review shared access keys before restarting. A nonempty environment key must contain 32–4096 visible ASCII characters without whitespace and cannot use the recognizable placeholder prefixes listed in the [configuration reference](../README.md#configuration-reference); an invalid value stops startup. Empty first-boot configuration generates a random 32-byte key. An invalid legacy stored key keeps administrator sign-in available but denies tunnel authentication until rotation, and must be replaced before saving Settings. Generate a random replacement and update all clients; length alone does not establish entropy.

Pre-authentication WebSocket upgrades are limited to 60 attempts per IP per minute across both tunnel routes and administrator live updates, independently of HTTP login throttling. For systemd, explicitly set absolute `DATA_DIR` and `SQLITE_PATH`, `INTERNAL_HOST=127.0.0.1` and `AUTO_FIREWALL=false` in `/etc/private-tunnel/server.env`; `EnvironmentFile=` can supersede unit defaults. Changing `DATA_DIR` does not override an explicit SQLite path. The initial control root is fixed at `/_private-tunnel`, not seeded from `.env`.

Use the [changelog](../CHANGELOG.md) for the change list and [deployment guide](README.md) for TLS, Nginx, systemd and Linux container setup.

## Preparing artifacts

1. Review the final diff and ensure no secrets or runtime databases are tracked. Confirm `package.json` and lockfile use the same version.
2. Run `npm ci`, `npm test` and the appropriate platform build. Test starting/stopping an HTTP tunnel and a TCP tunnel against an isolated server with the intended proxy configuration.
3. Run the **Prepare release artifacts** workflow manually on the reviewed commit, or after an owner creates a matching `v1.1.0` tag. Tag and package versions must match. The workflow has read-only repository permissions and uploads workflow artifacts only.
4. Download the source archive and complete unsigned Windows archive with their checksums. Inspect the archive contents and verify the checksums. Workflow artifacts expire after 30 days; retain reviewed release assets separately if needed.
5. Before broad public distribution, configure and verify Windows code signing and macOS signing/notarization, and perform the remaining target-platform and operational validation. Publishing a remote release is an owner action outside this preparation workflow.

The current Windows executable is an unsigned development build. Include the entire unpacked application folder. A source archive is generated from the selected Git commit; uncommitted local edits are not part of it. Linux/macOS desktop and CLI binaries are not generated by this release workflow.

## Remaining constraints

- One shared access key, no authenticated tenant identity or individual revoke/expiry.
- Public TCP has no built-in encryption or visitor authentication; secure the published service itself.
- No UDP, application WebSocket passthrough, HA or horizontal scaling.
- No complete load test, independent security certification or public-service abuse workflow is implied by the test suite.
- Signing, notarization, auto-updates and remote publication remain unconfigured.

Keep these constraints in any eventual public release description. Do not describe this candidate as ready for untrusted multi-user production hosting.
